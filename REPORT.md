# Лабораторная работа: Context Engineering — AGENTS.md и reusable skill

**Проект:** Task Management System  
**Репозиторий:** https://github.com/dmgrch/task-management-system  
**Исходный коммит (`lab-base`):** `42c1a821fe858151c749a90f76cb869f3e1e997c`  

## 1. Цель работы

Проверить, как явно заданный проектный контекст влияет на соблюдение конвенций кодовой базы автономным агентом Codex. Сравниваются независимые реализации одной API-задачи **без** проектных инструкций и **с** `AGENTS.md` и reusable skill. Дополнительно проверяется перенос инструкций на другую задачу (generalization).

## 2. Характеристика репозитория

Проект представляет собой систему управления проектами и задачами на C# / ASP.NET Core (.NET 9), EF Core и PostgreSQL, с автоматическими тестами на xUnit. В репозитории есть два сервиса — `UserAccessService` и `ProjectTaskService`. Для задач уже существуют `TasksController`, `ITaskService`/`TaskService`, `ITaskRepository`/`TaskRepository`. В то же время более старый `ProjectsController` непосредственно использует `ProjectTaskDbContext`: архитектура исходного проекта неоднородна.

Перед экспериментом был подготовлен и проверен исходный коммит `42c1a82` с тегом `lab-base`. Для всех запусков исходным состоянием служил этот коммит (для запусков с контекстом — тот же код с добавленными файлами инструкций).

## 3. Методика эксперимента

### 3.1. Контроль условий

- **Агент:** Codex Desktop, локальный режим работы с репозиторием.
- **Основная задача:** доработка `GET /projects/{projectId}/tasks`.
- **Независимые прогоны:** три baseline-попытки и три context-попытки в отдельных Git-ветках и новых сессиях агента.
- **Промпт:** одинаковый функциональный запрос для всех шести запусков.
- **Базовое состояние:** ветки baseline созданы от `lab-base`; ветки context — от `context-setup`, в которой относительно `lab-base` добавлены только `AGENTS.md` и `.agents/skills/implement-api-endpoint/SKILL.md`.
- **Фиксация:** каждое решение сохранено отдельным коммитом, diff и логами сборки/тестов.

### 3.2. Функциональная задача

Требовалось добавить к `GET /projects/{projectId}/tasks` параметры `page` (по умолчанию 1), `limit` (по умолчанию 20, максимум 100) и необязательный фильтр `status` по `TaskItemStatus`. Ответ должен иметь поля `items`, `page`, `limit`, `totalCount`, `totalPages`. Также требовались стабильная сортировка по `CreatedAt`, затем `Id`; исключение логически удалённых задач; HTTP 400 с кодом `VALIDATION_ERROR` для некорректных параметров; сохранение существующих проверок прав и обработки отсутствующего проекта; автоматические тесты.

**Принцип:** промпт описывал *что* реализовать, но не навязывал выбор слоя реализации.

## 4. Выявленные проектные конвенции

На основании исходных `TasksController`, `TaskService`, `TaskRepository`, DTO и других компонентов были сформулированы следующие правила:

1. **Границы слоёв:** новая функциональность задач использует Controller → Service → Repository; контроллер обрабатывает HTTP, сервис — бизнес-правила, репозиторий — EF Core-запросы.
2. **Авторизация:** защищённые операции проверяют доступ через `IUserAccessClient` и соответствующий `ProjectAction`, сохраняя существующие ответы об ошибках.
3. **Soft delete:** обычные выборки исключают задачи с `IsDeleted = true`, включая подсчёт агрегатов.
4. **Типизированные DTO:** публичные модели размещаются в `Dtos`; сущности EF Core не возвращаются напрямую в новых API-контрактах.
5. **Структурированные ошибки:** ошибки имеют поля `code` и `message`; ошибки валидации используют HTTP 400 и `VALIDATION_ERROR`.
6. **CancellationToken:** токен отмены передаётся от контроллера к сервису, репозиторию и асинхронным вызовам.
7. **История изменений:** для операций создания и изменения задач сохраняется существующая модель `TaskHistory` и `TaskChangeType`; операции чтения не должны создавать историю.

**Особенности применимости:** старый код `ProjectsController` частично нарушает строгую слоистость. Поэтому правило 1 применяется к *новому поведению задач*, а не ретроспективно ко всему репозиторию. Правило истории изменений неприменимо к основной задаче чтения списка. Обновление OpenAPI выделено как дополнительная процессная конвенция для изменений публичного API.

## 5. Созданный контекст

В ветке `context-setup` добавлены:

- `AGENTS.md` — карта проекта, семь конкретных конвенций, требования к тестам и документации, команды сборки и проверки.
- `.agents/skills/implement-api-endpoint/SKILL.md` — переиспользуемая процедура изменения HTTP API: исследование существующего контракта → реализация через подходящие слои → авторизация/валидация → DTO и OpenAPI → тестирование и проверка.

Инструкции сформулированы для класса API-задач, а не специально под параметры пагинации.

## 7. Проверка генерализуемости (generalization)

### 7.1. Новая задача

В отдельной новой сессии Codex с теми же проектными инструкциями поставлена другая задача: реализовать `GET /projects/{projectId}/tasks/statistics`, возвращающий общее количество неудалённых задач и распределение по четырём статусам (`todo`, `inProgress`, `review`, `done`). Требовалось учитывать только выбранный проект, сохранять авторизацию и обработку отсутствующего проекта, добавить тесты.

Запуск сохранён в ветке `generalization-attempt-1`, коммит **`e388afb`** (`Generalization - task statistics endpoint`).

### 7.2. Результаты изучения реализации

Изменено **8 файлов**: `TasksController`, `ITaskService`, `TaskService`, `ITaskRepository`, `TaskRepository`, новый `TaskStatisticsResponse`, тесты `TaskServiceTests` и OpenAPI-спецификация.

В контроллере добавлен абсолютный маршрут:

```csharp
[HttpGet("/projects/{projectId:guid}/tasks/statistics")]
```

В сервисе перед получением статистики проверяются существование проекта и доступ:

```csharp
await GetProjectAsync(projectId, ct);
await CheckAccessAsync(actorUserId, projectId, ProjectAction.ViewTask, ct);
var counts = await _tasks.GetTaskCountsByStatusAsync(projectId, ct);
```

Ответ формируется через типизированные `TaskStatisticsResponse` и `TaskStatisticsByStatusResponse`, у которых присутствуют свойства для всех четырёх статусов, включая нулевые значения. Данные запрашиваются через репозиторий; `CancellationToken` передаётся дальше по цепочке.

### 7.3. Тесты generalization

Codex добавил шесть тестов сервиса:

1. Пустой проект: все четыре счётчика равны нулю.
2. Подсчёт по статусам только для заданного проекта.
3. Исключение логически удалённых задач.
4. Отсутствующий пользователь: `USER_ID_REQUIRED`.
5. Отсутствие права доступа: `ACCESS_DENIED`.
6. Отсутствующий проект: `PROJECT_NOT_FOUND`.

Результаты локальной проверки:

- **Сборка:** `BUILD_EXIT=0`, **0 warnings**, **0 errors**.
- **Тесты:** `TEST_EXIT=0`, **30/30 пройдено** (14 `UserAccessService.Tests` и 16 `ProjectTaskService.Tests`).

**Вывод о переносе:** при выполнении новой задачи агент снова использовал разделение Controller → Service → Repository, DTO, существующую авторизацию, тесты и OpenAPI. Это свидетельство применимости контекста за пределами основной задачи пагинации.


## 8. Вывод

В данном эксперименте добавление конкретных проектных инструкций `AGENTS.md` и reusable skill сопровождалось существенным улучшением соблюдения **измеряемых статических конвенций**: среднее число флагов снизилось с **1,33 до 0,00 на запуск**. Основное различие состояло в архитектурном решении: во всех трёх запусках с контекстом Codex использовал сервисный и репозиторный слои, чего не наблюдалось ни в одной baseline-попытке.

Все шесть реализаций успешно прошли сборку и собственные тесты. Отдельная задача по статистике задач также была реализована с соблюдением изученных архитектурных правил; её сборка завершилась без ошибок и предупреждений, а 30 тестов прошли успешно.

Следовательно, **конкретный проектный контекст полезен для направления архитектурных решений агента**, даже если агент и без него может написать собирающийся код.
